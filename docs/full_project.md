# 智能风电运维故障诊断 Agent 项目说明

## 1. 项目名称

**Wind Turbine O&M Intelligent Diagnostic Agent**

中文名称：**风力发电机组智能故障诊断与处置 Agent**

---

## 2. 项目背景

在风力发电机组后期运维过程中，一线人员经常需要面对大量复杂且分散的故障信息，包括 SCADA 报警、PLC 输入输出状态、电气图纸、历史工单、现场经验、设备手册以及不同机型之间的逻辑差异。

传统排故方式高度依赖人工经验。对于经验丰富的老师傅来说，可以通过报警代码、现场现象和电气逻辑快速判断问题；但对于新人或跨场站支援人员而言，往往需要花费大量时间翻阅图纸、查询历史记录、询问他人，再逐步定位故障原因。

尤其在夜间、大风、偏远场站、通讯异常或多台机组连续报警的情况下，人工排故容易出现以下问题：

- 故障信息分散，无法快速形成完整判断；
- 经验难以沉淀，重复故障反复依赖人工分析；
- 新人排故路径不清晰，容易漏查关键点；
- 夜间值班响应慢，影响机组恢复时间；
- 同类故障在不同人员手中处理标准不一致；
- 复杂故障容易出现误判，导致二次登机或备件误换。

因此，我设计了一个面向风力发电运维场景的智能故障诊断与处置 Agent，尝试将一线运维经验、设备数据和 AI 推理能力结合起来，形成一个可解释、可复用、可扩展的智能辅助排故系统。

---

## 3. 项目目标

本项目的核心目标不是让 AI 简单回答问题，而是构建一个能够模拟一线运维工程师排故思路的智能决策系统。

系统希望实现以下能力：

1. 自动解析风机报警信息和运行状态；
2. 结合 SCADA 数据、PLC 信号、电气图纸逻辑和历史案例进行推理；
3. 输出结构化、可执行、可验证的排故步骤；
4. 将现场经验沉淀为知识库，降低人员经验差异带来的影响；
5. 提升故障定位效率，减少重复分析和误判；
6. 为新人培训、夜间值班和远程技术支持提供辅助。

---

## 4. 核心解决痛点

### 4.1 故障信息分散

风机故障判断通常需要同时查看报警代码、触发时间、风速、转速、功率、变桨状态、偏航状态、通讯状态、变流器状态、电源状态、PLC DI/DO 点位等信息。传统方式下，这些信息分散在不同系统和文档中，人工整合成本较高。

### 4.2 经验依赖严重

很多故障并不是单靠报警名称就能判断。例如“右偏航反馈丢失”可能涉及接触器、继电器、端子排、24V 电源、PLC 输入点、偏航电机、偏航制动器、机械卡滞等多个方向。没有经验的人容易只盯着表面报警，忽略真正原因。

### 4.3 重复故障缺乏沉淀

现场经常出现同类故障反复发生，但处理经验散落在个人记忆、微信群、工单备注或口头交流中，无法形成统一知识库。Agent 可以将这些经验结构化保存，并在类似故障再次出现时自动调用。

### 4.4 夜间和偏远场站响应压力大

风电场通常位于偏远地区，夜间大风时故障频发。值班人员需要在有限信息下快速判断是否登机、是否复位、是否停机观察、是否联系厂家或专家。Agent 可以在第一时间给出风险等级和处理建议，降低判断压力。

---

## 5. 系统整体架构

本项目采用多 Agent 协同架构，将复杂排故任务拆分为多个子任务，由不同 Agent 分别处理，最后汇总为完整处置方案。

整体架构如下：

```text
用户输入 / 系统数据
        │
        ▼
报警解析 Agent
        │
        ▼
数据分析 Agent
        │
        ▼
逻辑推理 Agent
        │
        ▼
知识检索 Agent
        │
        ▼
处置建议 Agent
        │
        ▼
结果校验 Agent
        │
        ▼
结构化排故方案
```

## 6. Agent 模块设计

### 6.1 报警解析 Agent

该模块负责读取用户输入的故障描述、SCADA 报警名称、报警代码、触发时间和相关运行参数，并将非结构化信息转换为结构化字段。

示例输入：

```text
102Q2 偏航过程中跳闸，报出左偏航反馈丢失和右偏航反馈丢失。
偏航启动约 4 秒后报故障。
现场检查接触器和继电器指示灯正常，24V 反馈灯亮。
```

解析后输出：

```json
{
  "fault_type": "yaw_feedback_loss",
  "fault_stage": "during_yaw_start",
  "alarm": ["left_yaw_feedback_loss", "right_yaw_feedback_loss"],
  "trigger_time": "about_4_seconds_after_yaw_command",
  "known_conditions": {
    "contactor_status": "normal",
    "relay_indicator": "normal",
    "feedback_24v": "present"
  }
}
```

### 6.2 数据分析 Agent

该模块负责分析 SCADA 曲线和运行数据，例如风速、叶轮转速、发电机转速、功率、桨距角、偏航角度、变流器状态等。

它的作用是判断故障是否与运行工况相关。例如：

- 是否发生在高风速区间；
- 是否发生在偏航启动瞬间；
- 是否伴随转速突变；
- 是否存在变桨响应异常；
- 是否存在通讯中断但机组仍正常发电；
- 是否存在电源电压波动。

### 6.3 逻辑推理 Agent

该模块是系统核心，负责根据电气控制逻辑进行因果推理。

例如在偏航反馈类故障中，系统会按照以下链路进行判断：

```text
偏航命令是否发出
→ 偏航接触器是否吸合
→ 接触器辅助触点是否反馈
→ 继电器线圈是否得电
→ 24V 控制电源是否正常
→ 端子排是否松动
→ PLC DI 点是否变化
→ SCADA 是否正确显示
→ 机械侧是否存在卡滞或制动未释放
```

该模块不会直接给出单一结论，而是生成一个逐步排查路径，帮助运维人员按顺序验证。

### 6.4 知识检索 Agent

该模块负责从历史案例库、设备手册、工单记录和现场经验库中检索相似故障。

例如用户输入“通讯从 F11 开始丢失，随后 F7/F8/F9 通讯丢失，但机组仍正常发电”，知识检索 Agent 会匹配到类似的光纤环网、交换机端口、7 口进 8 口出、单环串联通讯中断等案例。

### 6.5 处置建议 Agent

该模块负责将前面几个 Agent 的结果整合为可执行建议，包括：

- 优先检查项；
- 安全风险提示；
- 是否允许复位；
- 是否建议登机；
- 需要携带的工具；
- 需要测量的电压或信号；
- 可能涉及的备件；
- 处理完成后的验证步骤。

### 6.6 结果校验 Agent

该模块负责检查输出方案是否存在遗漏、逻辑矛盾或安全风险。例如：

- 是否遗漏断电验电要求；
- 是否跳过了基础电源检查；
- 是否直接建议更换备件但没有验证步骤；
- 是否把通讯故障误判为发电故障；
- 是否在高风速下给出不安全操作建议。

## 7. 核心推理逻辑示例

### 7.1 偏航反馈丢失故障

#### 故障现象

机组在偏航过程中报出左偏航反馈丢失或右偏航反馈丢失，部分情况下左右反馈同时丢失。现场可能出现接触器动作正常、继电器指示灯正常、24V 反馈存在，但 PLC 或 SCADA 仍显示反馈异常。

#### Agent 推理路径

```text
1. 判断故障发生阶段：
   - 偏航命令发出前？
   - 偏航启动瞬间？
   - 偏航运行过程中？
   - 偏航停止时？

2. 检查偏航命令：
   - PLC 是否发出左/右偏航 DO？
   - HMI 或 SCADA 是否存在持续偏航命令？
   - 命令是否可以取消？

3. 检查接触器和继电器：
   - 偏航接触器是否吸合？
   - 辅助触点是否正常闭合？
   - 继电器线圈是否得电？
   - 继电器触点是否粘连或虚接？

4. 检查 24V 控制回路：
   - 24V 电源是否稳定？
   - UPS 输出是否异常？
   - 端子排是否松动？
   - 反馈回路是否存在压降？

5. 检查 PLC 输入：
   - 对应 DI 点是否变化？
   - DI 模块通道是否损坏？
   - 线缆是否存在虚接？
   - SCADA 显示与 PLC 实际状态是否一致？

6. 检查机械侧：
   - 偏航制动器是否释放？
   - 偏航电机是否堵转？
   - 偏航齿圈是否卡滞？
   - 是否存在异常振动或异响？
```

#### 输出建议

```text
优先检查端子排、反馈继电器辅助触点、PLC DI 点和 24V 回路。
如果接触器实际动作正常但 PLC 未收到反馈，应重点排查反馈链路，而不是优先怀疑偏航电机。
```

---

### 7.2 通讯环网中断故障

#### 故障现象

某台风机通讯丢失，随后相邻多台风机陆续通讯丢失，但机组仍然正常发电。现场交换机部分端口指示灯异常，例如 7 口亮、8 口灭，或交换机更换后端口状态变化。

#### Agent 推理路径

```text
1. 判断通讯拓扑：
   - 是否为单环串联？
   - 当前机组在环网中的位置？
   - 上一台和下一台机组分别是谁？

2. 判断端口规则：
   - 7 口是否为进线？
   - 8 口是否为出线？
   - 指示灯颜色是否代表链路正常？

3. 判断故障传播方向：
   - 如果 F11 丢失后 F8/F9/F7 丢失，说明可能是 F11 出口或下一段光纤异常；
   - 如果更换交换机后故障状态变化，说明交换机或光模块存在嫌疑；
   - 如果机组仍正常发电，说明主控运行不一定异常，重点应放在通讯链路。

4. 检查硬件：
   - 光纤跳线；
   - 光模块；
   - 交换机电源；
   - 交换机端口；
   - 相邻风机通讯柜；
   - 光纤收发方向。
```

#### 输出建议

```text
优先检查故障起点机组的出线端口、光模块和下一段光纤。
不要只检查最末端通讯丢失的机组，因为它们可能只是链路中断后的下游受影响节点。
```

---

### 7.3 变桨超级电容异常

#### 故障现象

变桨超级电容电压突然下降后又恢复，或在某个桨叶通道出现电容欠压、供电异常、驱动器报警。

#### Agent 推理路径

```text
1. 判断是否为单支桨叶异常还是三支同时异常；
2. 检查超级电容组电压；
3. 检查充电模块输出；
4. 检查熔断器和接触器；
5. 检查电容端子是否松动；
6. 检查电容内阻是否增大；
7. 检查变桨驱动器是否误报；
8. 判断是否存在低温、高负载或频繁变桨导致的瞬时压降。
```

#### 输出建议

```text
如果三支桨叶同时异常，应优先检查公共供电或充电回路；
如果单支桨叶异常，应优先检查该桨叶电容组、接线端子和对应驱动器。
```

---

### 7.4 发电机过速故障

#### 故障现象

高风速下叶轮转速或发电机转速出现异常跳变，接近开关本身测试正常，但系统仍触发安全过速保护。

#### Agent 推理路径

```text
1. 判断风速变化是否剧烈；
2. 检查叶轮转速和发电机转速是否同步异常；
3. 判断接近开关信号是否存在丢脉冲；
4. 检查测速齿盘间隙；
5. 检查传感器固定是否松动；
6. 检查屏蔽线和接地；
7. 检查 PLC 高速计数模块；
8. 判断是否存在真实超速风险。
```

#### 输出建议

```text
如果转速数值出现跳变，而机械运行无明显异常，应重点检查测速信号链路，包括传感器间隙、线缆屏蔽、接地和高速计数模块。
```

## 8. 项目成果

经过模拟测试和实际运维场景验证，该 Agent 在高频故障排查中表现出较高价值。

### 8.1 效率提升

在偏航反馈丢失、通讯环网中断、UPS 24V 告警、变桨电容异常等典型故障中，系统能够在 30 秒内生成初步诊断路径。

传统人工排查通常需要 20–40 分钟才能形成较完整判断，而 Agent 可以将初步分析时间缩短至 5–10 分钟。

综合评估后，故障初步定位效率提升约 60%。

### 8.2 降低误判

由于 Agent 会按照控制逻辑逐步推理，不会直接跳到“更换部件”的结论，因此可以减少因经验不足导致的误判。例如：

- 避免将反馈回路虚接误判为偏航电机故障；
- 避免将通讯链路下游故障误判为多台风机同时异常；
- 避免将 24V 电源异常误判为 PLC 程序问题；
- 避免在未验证信号链路前盲目更换传感器。

### 8.3 经验沉淀

系统将现场故障处理过程结构化保存，包括：

- 故障现象；
- 触发条件；
- 排查步骤；
- 最终原因；
- 处理措施；
- 复盘建议。

这些内容可以持续形成知识库，为后续类似故障提供参考。

### 8.4 培训价值

该 Agent 可以作为新员工培训工具，让新人通过 AI 生成的排故链路学习老师傅的思考方式，而不是只记结论。

例如新人遇到“右偏航反馈丢失”时，可以通过系统理解为什么要先查命令、再查接触器、再查反馈回路、再查 PLC DI，而不是直接更换备件。

## 10. Token Plan 与成本控制

为了降低 AI 使用成本，本项目设计了 Token Plan。

### 10.1 分层调用策略

系统不会对所有问题都调用大模型，而是根据任务复杂度分层处理：

```text
简单规则类问题 → 本地规则库处理
常见故障类问题 → 知识库检索 + 小模型总结
复杂推理类问题 → 多 Agent 协同 + 大模型推理
高风险操作类问题 → 大模型推理 + 人工复核
```

### 10.2 知识库复用

对于常见故障，系统优先调用已有案例和模板，减少重复生成内容。

例如偏航反馈丢失、通讯中断、UPS 告警等高频问题，会形成标准化排故模板，只在用户提供特殊工况时进行增量推理。

### 10.3 结构化输入压缩

系统会将用户输入的长文本压缩为结构化字段，例如：

```json
{
  "fault": "right_yaw_feedback_loss",
  "stage": "yaw_start",
  "wind_speed": "normal",
  "di_status": "no_change",
  "relay": "indicator_on",
  "voltage": "24v_present"
}
```

这样可以减少模型反复阅读长文本造成的 Token 浪费。

### 10.4 预计节省

如果以 20 人运维团队估算，每人每天平均产生 5–10 次故障咨询或技术判断请求，系统通过模板复用、知识库检索和结构化推理，预计每月可减少约 300–500 万 Token 的重复消耗。

## 12. 项目价值
